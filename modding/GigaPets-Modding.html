Getting started

A mod is a folder in mods/ next to the game. Everything in it is plain text and pictures: there is nothing to compile.

mods/
  mymod/
    manifest.json        the mod's name and version (required)
    icon.png             32x32 picture for the Mods screen (optional)
    data/                JSON files: new and changed things (items, NPCs, areas, texts ...)
      items.json
    scripts/             Lua files: what the things do
      main.lua
    shaders/             .frag files (graphics effects, optional)
    audio/               sounds and music (optional)

The folder name must be the mod's id, and the id is lowercase letters, digits and _ (mymod, glow_pack). base is the game itself and cannot be used.

A first mod

mods/mymod/manifest.json:

{
  "id": "mymod",
  "name": "My First Mod",
  "version": "1.0",
  "game_api": "1",
  "description": "Says hello when the game starts."
}

mods/mymod/data/texts.json: a list of records. This one adds a line of text:

[
  { "type": "text", "mode": "add", "id": "mymod:str/hello", "text": "Hello from my mod!" }
]

mods/mymod/scripts/main.lua: a hook that shows it when a game starts:

local G = Game.hooks()

function G:onLoad(ctx)
  say("mymod:str/hello")
end

Start the game. The text appears when you load or start a game, and mymod is listed under Mods on the title menu.

Checking your work

gigapets.exe rom.u7 --validate-mods

loads the game and every mod (data and scripts), prints each error and warning with the file it came from, and exits with 1 if anything is wrong. Run it after every change: most mistakes (a misspelt field, an unknown id, a script that does not load) are found there before you start playing.

Where to go next

  • Manifest: every field of manifest.json.
  • Data records: how the JSON files work. The Data records reference lists every record type with its fields.
  • Scripting: hooks, ctx, the waiting functions, and what a script is allowed to do. The Lua API and Hooks references list everything.
  • Systems: change how the engine itself behaves (stats wearing down, the pet's steps ...) without touching its code.
  • Graphics: draw on the screen, add shaders, zoom the camera.

The manifest

manifest.json in the mod's folder. Only id and game_api are required.

Load order

Mods load in an order that puts every mod after what it requires and load_afters. Within that, the player's order from the Mods screen is used, and mods the player has not placed come alphabetically. A later mod can change what an earlier one made, so the order matters when two mods touch the same thing.

Switched-off mods

A player can switch a mod off on the Mods screen. It is not loaded at all: its data and scripts do not exist for that run. A mod that requires an off mod is left out too (the screen says why). What the mod saved stays in the save file and is back when it is switched on again.

Data records

Every .json file in mods/<id>/data/ is a list of records, read in file name order (so 01_items.json comes before 02_npcs.json). A record is an object:

{ "type": "item", "mode": "add", "id": "mymod:item/cake", "...": "fields of that type" }
  • type says what kind of thing it is. The Data records reference lists the types, with their fields.
  • mode says what to do with it. add makes something new. patch changes fields of one that exists (the game's or another mod's); fields you leave out stay as they were. replace swaps a thing (for an NPC or item, unlisted fields keep their values; for a text or sound it swaps the whole thing). remove takes one away. Each type says which of these it takes: for example npc takes add, replace and remove (not patch), minigame only patch, side_quest only add.
  • id names the thing. The ids a mod adds start with its own id and a colon: mymod:item/cake, mymod:npc/bob, mymod:str/hello. The game's own things are base:..., like base:area/3.

Rules the loader enforces

  • Only the fields a type lists are allowed. A misspelt field is an error naming the file and the record, not something quietly ignored.
  • A new id must not already exist and must use the mod's own prefix. An id may not contain spaces or control characters, or , = |.
  • One bad record does not stop the others from loading; every problem is reported (the game prints them, --validate-mods lists them).
  • Records can refer to each other across files and mods (an NPC to an area, an object to a scene). The loader applies the records in three passes, so a thing may be mentioned before the file that defines it: first texts, anims, tilesets, collision sets, object types, palettes and audio; then areas (they need a tileset and a collision set); then everything else (NPCs, items, objects, exits, quests ...). Inside a pass, files go in name order.

Texts and pictures

Texts are records too (type: "text") and are referred to by id everywhere: an NPC's lines, say("mymod:str/hello"), an item's name. A mod's PNG files are referred to by a path inside the mod's folder ("png": "art/cake.png"). A path cannot leave the mod's folder.

Changing the game's own things

Patch records change what the game has: base:area/3, base:room/4, base:item/.... Several mods may patch the same thing; they apply in load order, so the last one wins on a field they both set.

Seeing how the game's own things are made

The game can write its content out for you to look at and copy from:

  • gigapets.exe rom.u7 --export-base <folder>: the base game's areas, tiles and objects as JSON and PNG.
  • --export-music <folder>: the songs as MIDI files, and where each plays.
  • --export-instruments <folder>: what each instrument number sounds like.
  • --export-pet-frames <folder>: the pets' animation frames as pictures.

Each writes its files and quits.

Scripting

Scripts are Lua 5.4 files in mods/<id>/scripts/. They are loaded in file name order when the game starts. The top level of a script only registers things: hooks, options rows, a scene. Nothing in the game happens until the game calls a hook.

Hooks

A hook is a function on a table you get from the game. The game calls it when something happens and gives it one argument, ctx, describing the moment.

local G = Game.hooks()                  -- game-wide events
function G:onEnterArea(ctx)
  log("entered " .. ctx.area.id)
end

local bob = Npc.hooks("mymod:npc/bob")  -- one NPC
function bob:onTalk(ctx)
  say("mymod:str/bob_hi")
end

Game.hooks(), Npc.hooks(id), Area.hooks(id), Item.hooks(id) and Scene.hooks(id) each give your mod's own table, so two mods hooking the same thing never overwrite each other: both run, in load order. The Hooks reference lists every hook name and what its ctx holds. A name the game does not know is reported by --validate-mods (a typo like onEnterAera is found there, not by silence in the game).

Cancelling

Some hooks are "before" hooks (onBeforeDig, onBeforeBuy, onBeforeExit, onBeforeItemUse ...): return false cancels what the game was about to do. Hooks that only tell you something happened ignore what they return.

Waiting

Every hook runs as a coroutine, so it can wait without freezing the game:

  • say(textId [, vars [, opts]]): a dialogue box; the script carries on when it is closed.
  • ask(textId ...): a yes / no box; gives true or false.
  • wait(ticks): pause for some game ticks (30 a second).

A hook that waits has taken over from the game's own behaviour (as if it returned false) and carries on later. At most 8 scripts can be waiting at once; more are refused and reported.

What a script may use

Scripts run in a sandbox: Lua's string, table, math and utf8 libraries, and the game's own API (see Lua API). There is no io, os, debug, package, load or dofile, and math.random is not there: use rand.int(lo, hi) and rand.pick(list) so the game's randomness stays in one place. A script that runs too long (a million instructions in one call) is stopped with an error, and a script that uses too much memory is stopped too.

print(...) and log(...) write to the game's log (the console), with the mod's id in front.

Trusted mods

A mod can say "trusted": true in its manifest. Its scripts then also get io, os, debug, coroutine, load, loadfile, dofile, collectgarbage and require("name") (which loads scripts/name.lua of the same mod; dots are folders). Nothing is sandboxed any more: the mod can do whatever the player's account can. The Mods screen shows a trusted mod as trusted, so players know. Use it only when you need it (a mod that reads a file from disk, say).

Errors

An error in a script is logged with the mod, the hook and the line, and the hook is skipped; the game goes on. --validate-mods loads every script and checks hook names, so run it often.

Keeping values

  • save.get(key) / save.set(key, value): kept in the player's save slot.
  • profile.get(key) / profile.set(key, value): kept for the whole game, across slots.
  • player.setFlag / counter.*: flags and counters that belong to the pet's story (quests can watch them).

See the saves page for how they are stored and versioned.

Drawing and scenes

onHud, onPostWorld, onPostDraw and a scene's onDraw get a drawing object g. The graphics page covers it, and scene.open(id) / scene.close(result) open and close a screen of your own (a scene's onTick gets the keys). A scene can be opened from the front end too (see the front end page).

Systems: changing how the engine works

A system is one thing the engine does: a stat wearing down, the pet taking a step, an NPC choosing what to do, the Options screen changing a value. Hooks react to what happens; a system lets you change how it happens.

System.hooks(name) gives your mod's table for a system, with up to three functions:

local S = System.hooks("care.decay")

function S:before(ctx)      -- runs first; may change ctx, or return false to cancel everything
  if ctx.stat == "hunger" then ctx.amount = ctx.amount * 0.5 end
end

function S:replace(ctx)     -- does the job instead of the engine (the first mod to define one wins)
end

function S:after(ctx)       -- runs once it is done
end
  • ctx holds named numbers and strings (the Systems reference lists them for each system). The engine reads them back after before, so changing ctx.amount changes what the engine then does.
  • before returning false cancels the whole thing: no default, no replace, no after.
  • If a mod has a replace, the engine's own code is skipped and the replacement does the job; with none, the default runs with the values in ctx.
  • A system nobody hooks costs nothing and changes nothing.
  • System.list() returns every system with its fields, from inside a script.

An example: slower hunger

local S = System.hooks("care.decay")
function S:before(ctx)
  if ctx.stat == "hunger" then ctx.amount = ctx.amount * 0.5 end
end

Systems or hooks?

Use a hook to add something when an event happens (give a reward when a quest ends). Use a system to alter what the engine itself does (change how much a stat wears down, take over a step of the pet's movement). Many things are both: a hook tells you a quest was completed, the quest.reward system lets you change or cancel a step of its rewards.

The front end has systems too (frontend.menu, frontend.start, frontend.starter, frontend.name, frontend.options, frontend.boot, frontend.load, frontend.house, frontend.intro), listed in the same reference.

Graphics and shaders

Everything is a call on g inside a hook: Scene.hooks(id).onDraw(g) (the whole screen is the script's), Game.hooks().onHud(g) / Area.hooks(id).onHud(g) (over the world) and Game.hooks().onPostDraw(g) (over the finished frame, whole window; g.w, g.h = 320 x 240, or 426 x 240 in 16:9). At most 4000 calls a frame. Colours are { r, g, b [, a] }, 0..255.

Basics (as before)

g.clear(c) (scenes), g.rect(x, y, w, h, c [, fill = true [, mode]]), g.sprite(id, x, y [, opts]), g.text(id, x, y [, opts]), g.num(n, x, y [, opts]). mode = "blend" (default), "add" (lighten) or "mul" (darken / tint).

Sprite and blit options

{ scale = 2 | scaleX, scaleY, angle = degrees, pivot = { x, y }, tint = { r, g, b }, alpha = 0..1, mode, flip }. A sprite keeps its anchor at x, y and turns / scales around it (pivot = a point from the picture's top left instead).

Shapes

  • g.line(x1, y1, x2, y2, c [, width = 1 .. 64])
  • g.circle(x, y, radius, c [, fill = true [, mode]])
  • g.poly({ x1, y1, x2, y2, ... }, c [, fill = true [, mode]]): 3 to 64 corners, convex (filled as a fan from the first).

Canvases: offscreen pictures

g.canvas(name, w, h, function() ... end): the g calls inside draw into an empty offscreen picture of that size (1..2048 a side), in its own pixels. Canvases do not nest; the 8 used last are kept. Show one with g.blit(name, x, y [, { w, h, scale, angle, pivot, tint, alpha, mode, flip }]) (w, h fit it to a size; otherwise its own size) or on triangles with g.mesh. A canvas is drawn the frame it is made in (make it again each frame, or keep drawing it: it is yours until 8 newer ones push it out).

The frame as a picture: "@frame"

g.blit("@frame", ...) and g.mesh("@frame", ...) use the picture as it was when the list began. In onPostDraw that is the finished frame (world, menus, dialogue, other mods' HUDs), whole: what you cannot do with rectangles, you can do by drawing it again: zoom, rotate, shift, tint, blur (several offset blits with alpha), ghost trails, a split screen. Read back from the screen the frame it is asked for (not when no script uses it).

Meshes: warps

g.mesh(name, vertices [, triangles [, { mode }]]): vertices = { { x, y, u, v [, colour] }, ... } (u, v 0..1 over the picture; a colour tints that vertex), up to 4096; triangles = { i1, i2, i3, ... } (1-based; default: three vertices at a time). A grid of vertices moved by a sine is a water ripple; the demo is mods/gfxdemo.

The world camera: zoom and rotation

System.hooks('camera.view'): ctx.zoom (1 = as is; 0.25 to 4: below 1 more of the area shows) and ctx.angle (degrees) scale and turn the world around the middle of the view; the screens, dialogue and HUD stay as they are. The world is drawn into a picture of (view / zoom) and shown over the view, so zoomed pixels are big and crisp. Rotation shows black corners.

The front end (title, load, options)

The scripts of the mods are loaded for the title screens too, and the same g works there: Game.hooks().onHud and onPostDraw draw over every front-end screen with everything above. More than drawing:

  • Ticks and keys: Game.hooks().onTickStart / onTickEnd run there 30 times a second (ctx.state.menu is true, ctx.state.scene says if a scene is up, ctx.input / ctx.held are Z, X and the arrows; there is no world, so ctx.area.id is empty and ctx.pet zeros).
  • Scenes: scene.open("mymod:scene/id") (from a tick hook, or from a System.hooks("frontend.menu") hook that took the choice over) opens a Scene.hooks(id) of the mod over the whole screen: its onTick(ctx) gets the keys (ctx.input.z, x, left, right, up, down, and held), onDraw(g) draws, scene.close() ends it. While a scene is up the front end gets no keys. So a mod can add whole screens to the title: a "Mods" page, a custom new-game flow, a gallery. Example: a frontend.menu hook that, for choice "options", does scene.open(...) and returns false (cancel) to replace the options screen with its own.
  • Still fixed C++ there: the starter pick, name entry, the intro, the options screen's rows and the boot sequence (see docs/engine-map.md).

Shaders (OpenGL, GLSL 1.20)

A mod ships shaders/<name>.frag, registers it with { "type": "shader", "mode": "add", "id": "mymod:shader/wave", "file": "shaders/wave.frag" } and runs it from a script with g.shader("mymod:shader/wave", { strength = 0.5, tint = { 1, 0.9, 0.8 } }) (best in onPostDraw; it runs over everything drawn so far, so draws before it are affected and draws after it are not). The file is the shader's body: void main() { gl_FragColor = ...; }. Leave out #version (the game adds #version 120). The game gives it:

namemeaning
uv0..1 over the screen; y = 0 at the TOP
frame(vec2 p)the picture so far, sampled at p (same orientation as uv)
resolutionthe logical screen's size (320 x 240, or 426 x 240)
timeseconds since the game started
your namesuniform float / vec2 / vec3 / vec4, set from the table you pass (up to 16)
  • The renderer: SDL's own default on Windows is Direct3D, which cannot run GLSL. The game switches to SDL's OpenGL renderer when any mod has a shaders/*.frag (or with GP_RENDERER=opengl); GP_RENDERER=default keeps SDL's choice. If OpenGL cannot start, or the renderer is not opengl, shader passes are skipped and the log says so once.
  • A shader that does not compile is reported in the log with the driver's message the first time it is used, and skipped from then on.
  • Passes are GPU to GPU (the frame is copied inside the card, no read back). Several g.shader calls in a row work (each sees the result of the one before).
  • It works in the front end too. The demo is mods/gfxdemo/shaders/pp.frag (colour fringing, vignette, grade).

Layers: shading the world, the screens, or only one of them

The frame is built in layers, and a script may run drawing and shaders at two points:

  1. Game.hooks().onPostWorld(g): right after the world is drawn (zoomed / turned too), BEFORE the screens, dialogue, menus, the stat notice and the mods' onHud. A g.shader here shades the world only.
  2. Game.hooks().onPostDraw(g): after everything. A g.shader here shades everything so far.

To act on the screens only: in onPostWorld save the world with g.keep("world") (a canvas of the whole picture, pixel for pixel), then in onPostDraw run a shader that gets it as a second texture: g.shader("mymod:shader/ui", {}, { textures = { world = "world" } }). In the shader, uniform sampler2D world; and canvas(world, uv) read it (up to 4 extra textures, any canvas name); where frame(uv) differs from canvas(world, uv) the pixel was drawn by the screens (that is mods/gfxdemo/shaders/uitint.frag: world sepia from onPostWorld, screens inverted from onPostDraw). Order matters: g.keep saves the picture as it is at that point of the list, so keep after the world shader if you want the shaded world. A shader after another sees its result. In the front end there is no world: only onHud / onPostDraw.

Shaders on one thing of the world

world.shade(target, shaderId | nil [, uniforms]): a shader on the pet ("player"), on an NPC (its npc id) or on every object of a type (the object type id), until cleared with nil. The thing is drawn alone onto a transparent picture (384 x 384 px, feet at the middle / three quarters down) and that picture is drawn again over the same place through your shader, blended over the world. In the shader frame(uv) is the thing's own pixel (with its alpha), resolution the picture's size (384 x 384), time and your uniforms as usual: a glow outline, a recolour, a dissolve, a wobble. Its shadow, bubbles and overhead pictures are drawn separately and are not shaded. It works under a zoomed or turned camera too (the thing is shaded inside the world's picture). Limit: it needs the OpenGL renderer. Not saved: set it from a script when the game loads. The demo: mods/gfxdemo/shaders/glow.frag (a pulsing outline on the pet).

Options screen rows

A mod adds its own settings to the title's Options screen, above Done, with options.add at the top level of one of its scripts (only while the scripts load).

local function num(key, default) local v = profile.get(key); return v and tonumber(v) or default end

options.add("mymod:option/glow", {           -- the id starts with the mod's prefix
  label = "mymod:str/glow",                  -- a text record: the row's name
  kind  = "toggle",                          -- "toggle" (0 / 1), "choice" (an index from 0) or "slider" (a number)
  get = function() return num("glow", 0) end, -- the value now
  set = function(v) profile.set("glow", tostring(v)) end, -- the new value, after the player changed the row
})
options.add("mymod:option/style", { label = "mymod:str/style", kind = "choice", choices = { "mymod:str/soft", "mymod:str/strong" }, get = ..., set = ... })
options.add("mymod:option/power", { label = "mymod:str/power", kind = "slider", min = 0, max = 100, step = 10, get = ..., set = ... })
  • Left / Right (and Z on a switch or a choice) change a row: a switch flips, a choice cycles through choices (2 to 8 text ids), a slider steps by step within min..max.
  • Keep the value with profile.get / profile.set (saved for the whole game when the player leaves the screen), or anywhere else a script can: the game only calls get and set.
  • At most 8 rows in all mods. A row whose get or set fails (a script error) is logged and drops out of the screen.
  • The front end's own words (intro, house and load screens, Options labels, On / Off ...) are texts base:str/fe/<key> (list: src/game/frontend/fe_strings.hpp); reword one with a text record {"type":"text","mode":"replace","id":"base:str/fe/back","text":"Return"}.
  • System.hooks("frontend.options") (before / replace / after) sees every change of every row, the game's own too: ctx.row is "music", "sfx", "volume", "tutorials", "interpolate", "scale", "scale_mode", "window_mode", "aspect", "retro", "live", a mod row's id, or "" for a key row; ctx.forward (1 = Right or Z) and ctx.by_z. Cancelling it stops the change.
  • The same values are what the mod's game scripts read with profile.get: a setting set on the title screen is there in the game.

Pet activities

A mod starts an activity with player.startActivity(kind [, level]) (true if it started: false while the pet is busy with something else, in a room, in a dialogue or menu, or the kind is unknown). Each running activity then takes one step per tick through the system System.hooks("pet.activity") (ctx.kind, ctx.step; change ctx.step to jump, 0 ends it; replace skips the game's step so the mod can drive the pet with player.play). Checked in a real run: wash, question, potion, colour and feed each go through the steps below.

kindstartsteps (ctx.step)
feedstartActivity("feed")1 the first bite plays; 2 chewing, 4..9 more bites (one step for all of them); 3 the happy reaction, three times, then idle (+6 mood if it was food and mood < 0x1a)
washstartActivity("wash")1 a sitting pet gets up, then the bubble starts; 2 the bubble plays; 3 the happy reaction (cleanliness +100, the colour goes back to the original one)
potionstartActivity("potion")1 turn to the front; 2 the emote reaction with the exclamation bubble, then the shocked one
barkstartActivity("bark")1 turn to the front; 2 the species' call
questionstartActivity("question")1 the "?" bubble grows; 2 it waits (about half a second); 3 the answer bubble
trickstartActivity("trick", level) (1..3)1 turn to the front; 2 the trick plays (all repeats, the chain of the panda's level 3)
colourstartActivity("colour")1 turn to the front (it ends at once if the action key is not held); 2 the colour cycles while Z is held, and stops on the one showing

Notes

  • A step is a number the game's own code moves on; setting a step the sequence never uses (or one it only reaches with state it has not set up, like feed 2 without a feedRepeats) is the mod's responsibility. Values outside 0..999 are ignored.
  • While any of these runs (step not 0) the pet cannot be controlled, as in the game.

Saves and mod data

save.get / save.set (one slot) and profile.get / profile.set (the whole game) are kept as mod.<mod>.<key> in the save file / data/profile.txt.

  • A mod that is switched off (Mods screen) or removed keeps its values: the save is written with every key it was loaded with, so switching it back on finds them.
  • "data_version": N in manifest.json (default 1) versions those values. When a save made with an older data_version (or with values and no version = 1) is loaded, the mod's Game.hooks():onMigrate(ctx) runs once before onLoad (ctx.from, ctx.to; save.get / save.set work), then the save is stamped with N (mod.<mod>.__data_version). A mod that never raises data_version has no stamp. A save made with a newer data_version than the mod's is left alone and a message says so.
  • Profile values are not migrated (they are read by the front end too); keep them backward compatible.

The Mods screen

Title menu -> Mods (under Options). Lists every folder in mods/ that has a manifest.

Manifest fields it shows (all optional, name falls back to the id):

  • name - what the list shows
  • description - the box on the right
  • version, trusted - shown as before ("Trusted: runs freely" for trusted Lua)
  • icon.png in the mod's folder - 32x32, drawn next to the name

Keys (as the player has bound them): Up / Down move, Select switches the mod on / off, Menu enters order mode (Select picks a mod up, Up / Down move it, Select puts it down, Menu leaves), Cancel goes back.

What is chosen is kept in mods.txt in the data folder (order <id> lines, off <id> lines). It applies when mods load:

  • a mod that is off is not loaded; a mod that requires an off mod is left out too (the screen says why)
  • the order is the load order wherever requires / load_after allow it (a mod can not load before what it requires)
  • the game loads mods when a game starts, so changes show then; the title's own mods (front end scenes, strings) change on the next start of the program
  • --validate-mods ignores the state (it checks every mod)
  • frontend.menu gets choice = "mods"; the words are the texts base:str/fe/mods*

The front end (title screens)

The title menu, the intro, choosing a pet, naming it, picking a house, loading a game, Options and Mods are the front end. Mods can change much of it the same way they change the game.

Scripts run there too

Your scripts are loaded when the front end starts, and Game.hooks() ticks (onTickStart, onTickEnd), onHud and onPostDraw run on its screens as well (the tick counts from the start of the front end). A scene can be opened over any screen: it gets the keys and draws the whole screen.

local G = Game.hooks()
function G:onTickStart(ctx)
  if ctx.tick == 3 then scene.open("mymod:scene/splash") end
end

local S = Scene.hooks("mymod:scene/splash")
function S:onTick(ctx)
  if ctx.input.z or ctx.input.x then scene.close() end
end
function S:onDraw(g)
  g.clear({ 10, 40, 90 })
  g.text("mymod:str/splash", 30, 40)
end

While a scene is open it has the keys; the front end's own screen waits behind it. Shaders and onPostDraw drawing work over the title screens too.

Testing and sharing a mod

While you make it

  1. Put the folder in mods/ and run gigapets.exe rom.u7 --validate-mods. It prints every problem (the file, the record or hook, the reason) and a count at the end; it exits with 1 if anything is wrong, so you can run it from a script.
  2. Warnings are not failures: the common ones are a missing name, description or icon.png in the manifest, or a song using an instrument the game does not have. They are worth fixing, but the mod loads.
  3. Start the game and look at the Mods screen: the mod should be listed with its name, version, description and icon, and "N problems" in its info box if the loader found any when the game started.
  4. The game prints its log to the console; print and log from scripts end up there with [yourmod] in front.

Things that save time

  • Edit data and scripts, then use the Mods screen to switch the mod off and on: leaving the screen after a change reloads the title screen with the new set of mods.
  • A mod folder is the whole mod. To test with a clean setup, copy only that folder and the ones it requires into a fresh mods/.
  • --export-base <folder> and the other export flags (see Data records) show how the game's own content is written, the easiest way to learn a record type is to look at a real one.

Sharing

A mod is a folder: zip it (the folder itself, with manifest.json inside it) and send it. A player unzips it into their mods/ folder next to the game and switches it on under Mods.

Before you share:

  • Make sure --validate-mods reports 0 errors, with only the mods you require installed.
  • Give it a name, version, description and a 32x32 icon.png.
  • List what it needs in requires; list mods it should load after in load_after.
  • Raise version when you publish a change. If you changed how the mod's saved values look, raise data_version and handle the old ones in Game.hooks():onMigrate.
  • If the mod is trusted, say why in the description: players see that it is.

Compatibility

game_api is "1". A change to the game that removes or alters something a mod can use bumps the number before the dot; additions only bump the part after it. A mod written for 1 keeps working on every 1.x.

Example: the Berry Pie mod

A small complete mod, in modding/examples/berry_pie/. Copy the folder into mods/ to try it: it adds a food item with its own picture, gives the player one when a game starts, and makes hunger fall half as fast. Every file is shown here.

A picture is an anim: a list of frames, each a PNG from the mod. This one has a single frame. anchorX / anchorY is the point of the picture that sits at the position it is drawn at (0, 0 = its top-left corner, which is what an inventory icon wants).

[

]

The item. category puts it under the Food tab; use says what eating it does (food raises stats by the amounts in num: here hunger by 20 and happiness by 5); icon is the anim to draw. The picture on the ground defaults to the icon.

[
  { "type": "item", "mode": "add", "id": "berry_pie:item/pie", "category": "food",
    "name": "berry_pie:str/pie", "plural": "berry_pie:str/pies", "maxQty": 9, "price": 25,
    "icon": "berry_pie:anim/pie", "use": { "action": "food", "num": { "hunger": 20, "happiness": 5 } } }

scripts/main.lua

local G = Game.hooks()

-- When a game starts: give the player a pie if they have none, and say so.
function G:onLoad(ctx)
  if player.count("berry_pie:item/pie") == 0 then
    player.give("berry_pie:item/pie", 1)
    say("berry_pie:str/welcome")
  end
end

-- Hunger falls half as fast: change the amount before the engine applies it.
local S = System.hooks("care.decay")
function S:before(ctx)
  if ctx.stat == "hunger" then ctx.amount = ctx.amount * 0.5 end
end

Two ideas to notice:

  • Game.hooks() gives your mod's table; a function on it named after a hook (onLoad) is called when that happens. The Hooks reference lists them all.
  • System.hooks("care.decay") changes how the engine itself works. before can edit ctx (the engine reads it back) or return false to cancel.

Try changing it

  • Make eating the pie cure illness too: look at the use actions on the Data records page (medicine).
  • Put a text on the item with a description-like second line: add more text records and say them from an onItemUse hook (Item.hooks("berry_pie:item/pie")).
  • Give the pie only once: save.set("gifted", true) and save.get("gifted") keep a value in the save (see the saves page).

What mods can't do (yet)

Checked against the code on 2026-11-05. Items marked (project notes) come from the project's own notes and were not re-checked line by line. If something here is in your way, it is probably something that can be added: this list is also the list of what to ask for.

Data records

RecordModes it takes
textadd, replace, remove
animadd, replace, remove
npcadd, replace, remove
itemadd, replace
objectadd, patch, remove
areaadd, patch
speciesadd, patch
palette, shader, side_questadd
minigame, roompatch

The others are described on their own entries in the Data records reference.

  • Items cannot be removed or patched. Use replace (the fields you give change, the rest stay).
  • No new rooms. room only patches the eight the game has: the three player homes (base:room/0 to 2) and the four hotels (4 to 7). Furnishing and the door's return point can change, the number of rooms cannot.
  • Minigames can be tuned, not made. A minigame record changes the numbers and prize lists of one the game has. A new minigame is a scene in Lua (your own onTick / onDraw).
  • Areas are tile maps. There is no image-based area format. An area is a grid of tile numbers from a tileset and a collision set.
  • No interaction records. An object can show a sign text, a message, or open a scene; anything more is an onInteract hook.
  • No records for the pet's rules. Tricks, care, personality and befriending are not data you can add. Change how they work with systems (care.decay, trick., encounter., friend.* ...) and hooks, or set the pet's numbers from a script (player.adjustCare, player.setTricks ...).
  • Generated quests cannot use mod NPCs. The quest generator picks givers and receivers by the game's own NPC pool numbers, so a mod NPC cannot give or receive a generated quest (project notes). A side_quest record can use any NPC, and quest_spawn works with mod NPCs.
  • No custom fonts or UI art. Text is drawn with the game's fonts, and the title and menu pictures come from the ROM. A mod draws its own pictures and shapes with g, not new fonts.
  • Mod animations are recoloured only if you ask. A mod's anim takes the pet's colours only when its record has a palette; otherwise the pictures are drawn as they are. NPC species and the front end do not recolour mod animations yet (project notes).
  • Objects have no animation frames. To animate one, swap its type from a script (object.setType) (project notes).
  • NPC walking ignores walls. npc.walkTo does not steer around walls; a script asks area.walkable itself (project notes).
  • Audio. A mod instrument has no loop crossfade, and the pitch bend range is the game's own (project notes).

A script is sandboxed (see Scripting): no files, no os, no require, unless the mod is trusted.

Other limits:

  • Hooks and systems are the game's. A mod cannot define a new hook or system of its own; it works with the ones listed in the references. (Mods can share state through flags, counters and profile / save keys.)
  • math.random does not exist. Use rand.int and rand.pick, so randomness stays in one place.
  • Shaders need OpenGL. They are GLSL 1.20. The game picks the OpenGL renderer by itself when any mod has a shaders/*.frag file; the setting GP_RENDERER can force a driver.
  • One script state. Every mod's scripts run in one Lua state and share its global variables. Keep your state in local variables, save and profile, and give any global a name nobody else will use.

The front end

  • The title menu's entries are fixed (New Game, Load Game, Options, Mods). A mod cannot add a button, but frontend.menu can intercept a choice, and a scene can open from any screen. (Mods has no button art in the ROM, so it is drawn as text.)
  • The pictures and fonts of the title screens come from the ROM. Mods can draw over them (onPostDraw), reword them (base:str/fe/...), and shade them, not replace the originals.
  • A change in the Mods screen reloads the title screen when you leave it, not the running game. A game that is already running keeps the mods it started with until it is started again.

The engine itself

  • Mods do not patch the program. The engine is a reimplementation of the game, not the game's own code, so mods work through records, scripts, hooks and systems, the seams the engine offers. A part that has no hook or system cannot be changed by a mod.
  • game_api is a promise, not a guarantee of every detail. A mod keeps working across versions with the same major number; details the references do not mention can still change.

Hooks

A hook is a function a mod puts on a table; the game calls it when something happens. All of them get one argument, ctx, with what is known about the moment. Hooks run as coroutines, so say, ask and wait work inside them.

Game.hooks()

The game-wide table: local G = Game.hooks() then function G:onLoad(ctx) ... end.

onQuestComplete

The receiver took a quest's hand-in (the objectives are already removed), before the completion dialogue. Global: it fires for table quests and generated ones alike (ctx.quest.id is nil for a generated one). ctx.quest = { id, number, generic, type }, ctx.giver = { id }, ctx.receiver = { id }, ctx.player. return false skips the quest's built-in bonus rewards (the thank-you text and the next quest still follow).

onEnterArea

Fires Area.hooks(areaId).onEnter: the pet has arrived in the area (also when the game starts there). ctx.area = { id }, ctx.from = { id } (the area it came from; ctx.from.id is nil when the game just started). The result is ignored. Also fires Game.hooks().onEnterArea for every area, with the same ctx. Returns true if any script ran.

onLoad

Fires Game.hooks().onLoad: a game has just started from a slot (a new one or a loaded one) and the mod's save values are back (save.get works). This is where a mod puts its engine.set calls back. The result is ignored.

onSave

Fires Game.hooks().onSave: the slot is about to be written. save.set calls made here are written with it. Result ignored.

onBeforeDig

onBeforeDig(ctx): the pet is about to dig (Z on bare ground). ctx.x, ctx.y = where. Cancelled: nothing is dug.

onAfterDig

onAfterDig(ctx): the dig is over. ctx.x, ctx.y; ctx.result = "item" (something turned up), "dud" (a spot with nothing) or "miss"; ctx.item = { id } for "item" (the item that is now lying there to pick up).

onBeforePickup

onBeforePickup(ctx): the pet pressed Z on something lying on the ground. ctx.item = { id }, ctx.x, ctx.y. Cancelled: it stays.

onAfterPickup

onAfterPickup(ctx): the item went into the bag. ctx.item = { id }, ctx.x, ctx.y.

onBeforeBuy

onBeforeBuy(ctx): the pet pressed Z on a shop item it could buy. ctx.item = { id }, ctx.price (each). Cancelled: nothing happens.

onAfterBuy

onAfterBuy(ctx): the purchase went through. ctx.item = { id }, ctx.price (each), ctx.quantity.

onBeforeExit

onBeforeExit(ctx): the pet is about to go through a door. ctx.area = { id } (where it is), ctx.to = { id }, ctx.exit = { id }. Cancelled: the door stays shut (a door the pet walks into asks again only after it has stepped away). Say something with say().

onStatChange

onStatChange(ctx): money, a personality stat or a care stat is about to change. ctx.kind = "money" | "personality" | "care", ctx.stat = the stat's name as in player.care / player.personality (nil for money and for a stat that has no name), ctx.delta = the change, ctx.value = what it is now. Return a number to change by that instead, false to cancel the change; anything else leaves it. It cannot wait. Changes the hook makes itself (player.adjust...) are not passed through it again. Returns the delta to apply.

onBefriend

onBefriend(ctx): an NPC has just become the pet's friend (or greeted it again: ctx.again). ctx.npc = { id }. Result ignored.

onQuestAccept

onQuestAccept(ctx) / onQuestDecline(ctx): the player said yes / no to a quest. ctx.quest / giver / receiver as in onQuestComplete.

onQuestDecline

The player said no to a quest offer. ctx.quest, ctx.giver, ctx.receiver as in onQuestComplete. The result is ignored. (onQuestAccept is the yes.)

onQuestFail

onQuestFail(ctx): a side quest ran out of its time_limit (it is idle again; nothing was paid). ctx.quest / giver / receiver as in onQuestComplete.

onBeforeItemUse

onBeforeItemUse(ctx): the player chose "use" on ANY item, before the item's own Item.hooks(id).onItemUse and the game's handling. ctx.item = { id }. return false takes the use over (nothing is eaten or consumed unless the script does it); the item's own hook then does not run.

onSceneClose

A scene a mod opened has closed. ctx.scene = { id }, ctx.result = what scene.close(result) was given (a number, string or boolean; nil if nothing).

onMigrate

Saved values of this mod are older than its data_version in manifest.json. Runs once while a game starts, before onLoad. ctx.from = the version the save was made with (1 if it has values and no version), ctx.to = the mod's data_version. save.get and save.set work here: read the old values, write the new ones. Only the mod that raised its data_version is called. See the guide page on saves.

onHud

Every frame, over the walking world and the game's own screens (dialogue, menus; before onPostDraw): draw with g.rect, g.sprite, g.text, g.num and the shapes (not g.clear). Area.hooks(id).onHud(g) is the same for one area, drawn after the game-wide ones. At most 4000 draw calls a frame. See the graphics page.

onTickStart

The game-wide tick: runs first in every simulation step (30 a second), whatever is open. ctx = { tick, dt = 1/30, area = { id }, pet = { x, y }, state = { dialogue, menu, room, encounter, scene }, input, held } (state says what is open: true means the world is not running; input / held are the keys, at the start those of the previous step). Cheap work only: it runs 30 times a second.

onTickEnd

Runs last in every simulation step (also when the step stopped early, for a menu or a screen change). Same ctx as onTickStart.

onPostWorld

Draws over the finished world (tiles, objects, NPCs and the pet) but under the HUD, menus and dialogue. The g is the whole drawing object (shapes, canvases, "@frame", meshes, g.shader): this is where world-only effects go. See the graphics page.

onPostDraw

Draws over the finished frame, the whole window (world, HUD, menus, dialogue, other mods' drawing; g.w / g.h = 320 x 240, 426 x 240 in 16:9). g.shader(id, uniforms) here runs a full-screen shader over everything. See the graphics page.

One NPC: Npc.hooks("mymod:npc/bob").

Fires Npc.hooks(id).onTalkStart: the player pressed Z on the NPC, before anything else happens. return false from the script sets suppress: the game then skips its default handling of this talk (quest, hand-in, dialogue, befriending). Any other result, no hook, or a script error: the game carries on.

onTalk

Fires Npc.hooks(id).onTalk (the player pressed OK on the NPC's line). Returns true if a script ran. The return value of the script function is ignored. A script that errors is switched off for the rest of the session and the error is logged.

Fires Npc.hooks(npcId).onTick once per game tick while the NPC is in the area the pet is in and the world is running. ctx.npc = { id, x, y, facing, walking, scripted }, ctx.tick as for an area. The script drives the NPC with npc.walkTo / face / play / stop / release (and reads the pet with player.pos). If the last onTick is still waiting (wait / ask) no new one starts. True if a script ran.

One area: Area.hooks("base:area/3").

Fires Area.hooks(areaId).onInteract: the player pressed Z near an object in that area, before the game's own handling (the object's interaction, its sign text). return false takes over: the default is skipped. ctx.area = { id }, ctx.object = { id }, ctx.player. Any other result, no hook or an error: the game carries on.

Fires Area.hooks(areaId).onEnter: the pet has arrived in the area (also when the game starts there). ctx.area = { id }, ctx.from = { id } (the area it came from; ctx.from.id is nil when the game just started). The result is ignored. Also fires Game.hooks().onEnterArea for every area, with the same ctx. Returns true if any script ran.

onLeave

Fires Area.hooks(areaId).onLeave: the pet is going to another area. ctx.area = { id } (the one it leaves), ctx.to = { id }. The result is ignored; the area has not changed yet when this runs.

onTick

Fires Area.hooks(areaId).onTick once per game tick (30 a second) while the pet is in that area and the world is running. ctx.area = { id }, ctx.dt = seconds per tick (1/30), ctx.tick = ticks since the game started (30 a second, counting the ones skipped while a menu or dialogue was open). onHud

Like Game.hooks():onHud(g), but only while the pet is in this area; drawn after the game-wide HUD.

One item: Item.hooks("mymod:item/cake").

onItemUse

onBeforeItemUse(ctx): the player chose "use" on ANY item, before the item's own Item.hooks(id).onItemUse and the game's handling. ctx.item = { id }. return false takes the use over (nothing is eaten or consumed unless the script does it); the item's own hook then does not run.

Scene.hooks(id)

A scene a mod opens (a full-screen script): Scene.hooks("mymod:scene/shop").

onOpen

The scene has just opened (scene.open(id) from any script, or an object whose action is scene). If scene.open was given an argument it is ctx.arg. Set the scene up here; wait, say and ask work.

onTick

Every simulation step (30 a second) while the scene is open and the last onTick has finished. ctx = { input = { z, x, left, right, up, down } (pressed this step), held = { the same, true while held }, tick, dt = 1/30 }. Close the scene with scene.close(result).

onDraw

Every frame while the scene is open: the whole screen is the scene's. Draw with g (g.clear(c) first). A scene that fails closes itself.

Data records

Records are JSON objects in mods/<id>/data/*.json (each file is a list). Each has a type, usually a mode and an id. The ids a mod makes start with its own prefix (mymod:).

anim

An animation made of pictures from the mod. { "type": "anim", "mode": "add", "id": "mymod:anim/bob", "palette": 479, "frames": [ { "png": "art/bob1.png", "anchorX": 16, "anchorY": 40, "dx": 0, "dy": 0 }, ... ] }. Each frame is a png (a path inside the mod) with where the picture hangs from (anchorX, anchorY) and an offset (dx, dy). palette is a game palette number (257 to 4095, like 479 = the dog's colours): the pictures then take the pet's colours instead of staying as drawn. Modes: add, replace (starts over with the new frames), remove (references to it are not checked). NPC records point at an anim with anim.

Fields: type, mode, id, frames, palette

area

area: a map of 32 x 32 tiles. { name = text id, tileset, collision, map = [[row of tile numbers], ...], margins = [left, right, top, bottom] (default the base game's 42, 42, 62, 20), y_offset, music = a song 0..8 (default: keep the current one), spawn_points = [[x, y], ...] (where random finds may appear), max_events }. Width and height follow the map (1 to 255 tiles). instrument

---- instrument and drum records (the sounds a MIDI song is played with, see engine/midi.hpp) ----

  { type: "instrument", mode: "add", id: "mymod:instrument/harp", file: "audio/harp.wav", root: 60, loop_start: 0.4, loop_end: 1.1,
    attack: 0.005, decay: 0.2, sustain: 0.6, release: 0.1, volume: 100 }
  { type: "instrument", mode: "replace", id: "base:instrument/3", zones: [ {file: "low.wav", root: 48, top: 59, loop_start: 0.3}, {file: "high.wav", root: 72} ] }
  { type: "drum", mode: "add", id: "mymod:drum/clap", file: "audio/clap.wav", volume: 100, pitch: 0 }
  { type: "drum", mode: "replace", id: "base:drum/5", file: ... }

An instrument is one sample (file, root, ...) or zones: several, each for the notes up to its top (highest note, default 127). root: the MIDI note the sample sounds at (default 60 = middle C); the note played speeds it up or slows it down from there. With loop_start / loop_end (seconds of the file; end defaults to the file's end) a held note repeats that stretch until it ends, with none the sample plays once. attack, decay and release are seconds, sustain a level from 0 to 1. A drum is played from its start whatever the note (pitch only shifts it); it has no loop. The ROM's instruments are 0 to 13 and its drums 0 to 11 (replace them with "base:instrument/3" / "base:drum/5"); a mod's own come after, in the order they load: 14, 15... and 12, 13... Use these numbers in a music record's programs / drums / channels, or "Lead [i14]" in the editor's channel names.
